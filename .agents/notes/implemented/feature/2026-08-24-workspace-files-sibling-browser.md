# Agent Note: A Files tree sibling to a Workspace's session list, with in-app preview

Status: implemented

English | [中文](2026-08-24-workspace-files-sibling-browser.zh.md)

## Problem

The Web GUI's sidebar lists a Workspace's Sessions but has no way to see the files and subfolders under the Workspace's own directory — an operator who wants to check what a Workspace actually contains has to leave the app. The existing "browse the local filesystem" primitive, `ctx.directoryPicker`'s `browse` capability (`host.listDirectory`), exists specifically to let an operator pick a *workspace root* and is deliberately directories-only (`packages/host/directory-picker-browse`'s own dirent filter skips every non-directory entry) — reusing it verbatim can never show files. Widening that seam would also couple the workspace-creation picker's behavior to an unrelated, higher-exposure feature (an always-available read of arbitrary files under a Workspace, not a one-shot root selection).

## Decision

A new, independent `workspace.listEntries`/`workspace.readFile` RPC pair, implemented directly in `dsh-api-workspace-controller` (`packages/api/workspace-controller/src/files.ts`) against `node:fs/promises` — no new capability-seam package family, and `ctx.directoryPicker`/`host.listDirectory` are untouched. `listEntries` returns directories AND files for one level (directories first, then name-sorted within each group; each bucket independently bounded by `workspaceFilesMaxEntries`, default 1000). `readFile` returns `{ kind: 'text', content }` for valid UTF-8 or `{ kind: 'binary', mediaType, data: base64 }` otherwise, size-bounded by `workspaceFilesMaxReadBytes` (default 20MB, checked via a `stat` probe before the read) and failing `file-too-large` over the bound. Both take `workspaceId` and validate `path` is the workspace's own canonical root or a descendant of it (`isWithinWorkspace`, computed through `node:path.relative` so a sibling directory sharing a name prefix — `/ws` vs `/ws-2` — is correctly rejected) before touching the filesystem, answering `directory-unreadable` otherwise.

`ctx.workspaces` (the client runtime) exposes `listWorkspaceEntries`/`readWorkspaceFile` alongside its existing `listDirectory`/`openPath`. `ui-workspace`'s `SessionTree` renders a new `FilesNode` component as the first row under each real Workspace's header, sibling to its Session rows (the Ungrouped bucket and the flat "In one list" view have no single root path and render no Files node). Expanding it lazily fetches the workspace root's level; a directory row expands its own nested level in place (recursive `FilesLevel`, one `useLevel` fetch per mount — no `open` flag, because the caller only ever mounts the level while it is genuinely open); a file row opens `FileViewer`, an in-app preview dialog dispatching by extension (`packages/client/ui-workspace/src/client/files/classify.ts`): Markdown through the shared `MarkdownText`, recognized text/code extensions through `ReadBlock` (line-numbered, shiki-highlighted — the grammar map is a **local, small duplicate** of the `read` tool's `langFromPath`, not an import, because that mapping lives in `dsh-fs-tool-fs`, a host/model-tool package, and importing it would cross the client/host layering boundary for one pure function), images through a `URL.createObjectURL` blob built from the base64 payload. Everything else — PDF included, and any read whose classified kind disagrees with what the Host actually decoded — falls back to a single "Open with default app" action wired to the pre-existing `ctx.workspaces.openPath` (`host.openPath`, unchanged).

## Alternatives considered

- **Widen `host.listDirectory`/`ctx.directoryPicker` to report files.** Rejected: that seam's whole reason to exist is picking a workspace root (directories only, by its own documented policy); a persistent, always-on read of arbitrary files under a Workspace is a materially different exposure than a one-shot root-selection dialog, and conflating them would make the picker's behavior depend on a feature it has nothing to do with.
- **A new `ctx.<service>` capability seam mirroring `directoryPicker` (Service Definition + native/browse/auto backends).** Rejected as over-built: file listing has no OS-chooser equivalent to discriminate against, so there is only ever one implementation shape; a whole seam family for one implementation adds indirection with no current second consumer.
- **Route file listing/reading through `ctx.fs`.** Rejected: `ctx.fs` is the model-tool-facing storage seam (policy events, sandbox-swappable backends per session); riding it would couple GUI browsing to the model's confinement backend, and `ctx.fs`'s `FsTarget`-keyed API is not a natural fit for arbitrary-path GUI requests. `dsh-api-workspace-controller` does not depend on `ctx.fs`.
- **Import `langFromPath` from `dsh-fs-tool-fs`.** Rejected: that package is host/model-tool code; a browser-side component importing it crosses the client/host layering boundary this codebase enforces elsewhere. A ~15-line local duplicate of a pure, stable mapping is the cheaper and cleaner choice.
- **A real figma-extracted file icon.** Deferred: no such asset exists in `ui-primitives` yet (only folder icons, all real figma extracts) and inventing plausible-looking SVG geometry would violate the package's real-asset convention. `IconFilePlaceholder16` is an explicit placeholder pending a real design asset.
- **In-app PDF preview.** Deferred, not rejected: falls back to `openPath` for now; would need a new binary-serving route and a PDF.js or `<iframe>` embed, out of scope for this pass.
- **Streaming a sorted bounded window for `listEntries` (mirroring `directory-picker-browse`'s `boundedInsert`).** Rejected for this seam: `boundedInsert`'s `ListingCandidate` shape and its single-bucket assumption do not fit the directories+files two-bucket split without a parallel reimplementation; `listEntries` instead cuts each bucket in `readdir` arrival order once it fills, still sorting whatever it kept — a level under the bound is fully sorted, and a documented, non-name-sorted tail is accepted for a cut level.

## Consequences

- The wire gains `workspace.listEntries`/`workspace.readFile`, a new `file-too-large` error code (`path`, `maxBytes` details), and `WorkspaceEntry`/`WorkspaceEntryListing`/`WorkspaceFileContent` types exported from `dsh-api-workspace-controller`'s own `types.ts` and threaded straight through its `client/` face (`model.ts`/`service.ts`) to `ui-workspace`'s `FilesNode`/`FileViewer`; the package's own test fixtures serve a small deterministic file tree (text, Markdown, one binary/image) covering the preview matrix for keyless assembled tests.
- `WorkspaceController.Config` gains `workspaceFilesMaxEntries`/`workspaceFilesMaxReadBytes` (deployment-configurable per the no-hardcoded-tunables rule), both natural numbers with the stated defaults.
- A Workspace's Files tree is read-only: no create/rename/delete/move for files or folders, no search, and no persistence of expansion state across a browser remount (mirrors `ui-directory-picker-browse`'s "no search, no persistence" posture) — a future increment can add these without a wire change to the two RPCs already shipped.
- File-content reads are size-bounded at the Host before any byte leaves the process (`file-too-large` on the `stat` probe, before `readFile` runs), so a large file cannot be forced into browser memory through this path.
