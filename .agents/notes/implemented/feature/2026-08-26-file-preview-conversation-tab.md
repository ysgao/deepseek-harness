# Agent Note: File preview opens as a conversation tab, not a floating modal

Status: implemented

English | [中文](2026-08-26-file-preview-conversation-tab.zh.md)

## Problem

The Workspace Files tree ([sibling-browser Agent Note](2026-08-24-workspace-files-sibling-browser.md)) opened every file in `FileViewer`, a `Modal` dialog portaled over the whole page — floating chrome that covers the sidebar and conversation alike, and that a user cannot keep open beside the chat while reading a file. The main conversation area already has a real tab system for exactly this kind of alternate view: `ui-conversation`'s `conversation.view` slot (`kind: 'list', scope: 'session'`), used today by Chat and, when composed in, `ui-trajectory`'s ledger. Opening a file there instead — a `File` tab next to Chat — needed no new UI system, only a way to reach it from a click inside a different package's tree.

## Decision

**Presentation split, not duplication.** The file-content rendering logic (loading/error/too-large/external notices, image, Markdown, syntax-highlighted text) moves out of `ui-workspace`'s `FileViewer.tsx` into a new pure component, `FilePreview` in `ui-primitives` (cordis-free, no host or wire vocabulary — callers resolve their own fetch into the plain `FilePreviewState` union before rendering). `FileViewer.tsx` becomes a thin `Modal` shell around `FilePreview`; a new `FileView.tsx` wraps the same `FilePreview` as a tab pane, decoding image blob URLs and receiving `WorkspaceFileBrowseError`-aware `readFile` and its git/write siblings as injected props rather than resolving `ctx.workspaces` itself. `FileView.tsx` originally lived in `ui-conversation` alongside its `id: 'file'` registration; it was later extracted into its own package, `ui-conversation-files`, to match upstream's requirement that `ui-conversation`'s base `apply()` register no `conversation.view` entries by default — each concrete view, File included, is now a separately-mounted package that lazily injects into `conversation.view` only when composed in (mirroring how `ui-chat` supplies the `'chat'` view). The `File` tab (id `'file'`, order 5, between Chat at 0 and Trajectory at 10) registers in `ui-conversation-files/apply.ts` and shows an empty-state notice until first used, but — unlike this note's original design — is present only when `ui-conversation-files` is part of the running composition, not unconditionally.

**The cross-plugin trigger cannot write `conversationStore` directly.** `ui-slots` resolves and caches a declared store's bound-actions instance per `(entry, scope key)` pair inside `SlotRegistry`'s private `resolveStore`; there is no public `ctx.slots` method for `apply.ts`-level code in a *different* package to reach a live instance, and calling the store handle's own `.create(sessionId)` from outside mints a second, disconnected instance rather than the one components read. `ConversationStoreState` gains a `viewRequest: { view, focus } | null` field, written by a generic `openView(view, focus)` action (a superset of the file-specific one-shot field this note originally introduced, generalized so any view can request focus, not File alone) but nothing outside `ui-conversation` writes it directly. Instead, `ui-conversation` owns a small `FileOpenRegistryImpl` (`files/file-opener.ts`, one `Map<SessionId, SnapshotStore<{path,seq}>>`, the exact shape of the pre-existing `ComposerBlockRegistry`) and provides it through a new optional service, `ctx.get('conversationFileOpener')` (`ConversationFileOpener.openFile(sessionId, path): boolean`, the same optional-service convention as `chatFileMentions`). `ConversationSession` — which legitimately holds `conversationStore`'s bound actions for its own session, because it is one of that store's own registered components — subscribes to the registry's per-session source via a `hooks.pendingFileOpen` compartment and drains a pending request into `openView('file', path)` through its own effect.

`ui-workspace`'s `FilesNode` calls `ctx.get('conversationFileOpener')?.openFile(currentSessionId, path)` first (via a new `openInConversation` callback threaded through `WorkspaceBrowserInjected`/`WorkspaceBrowser`/`FilesNode`); a `false` result — no current session, or `ui-conversation` composed out of the bundle — falls back to the pre-existing `FileViewer` modal, so the Files tree keeps working standalone.

## Alternatives considered

- **`ui-conversation` reaches into `ui-workspace`'s `FileViewer`/`classify.ts` directly.** Rejected: `packages/client/AGENTS.md` forbids cross-package imports of another plugin's symbols outside the slot system and `ctx` services; `ui-workspace` is one client of `ctx.workspaces`, not the owner of file-reading concepts, so this direction was never actually necessary once `FilePreview` moved to the shared `ui-primitives` layer both packages already depend on.
- **`ui-workspace` registers the `conversation.view` tab itself** (mirroring `ui-trajectory`'s own-package registration). Rejected: the tab must read/write `conversationStore`'s `view`/`viewRequest` fields, which requires declaring `store: conversationStore` on the registration — a privilege of `conversationStore`'s owning package. `ui-workspace` cannot hold that store's bound actions without importing `ui-conversation`'s private store module, which the same cross-package rule forbids.
- **Duplicate `FilePreview`'s rendering logic into a second, `ui-conversation`-local component instead of extracting a shared one.** Rejected: `ReadBlock`/`MarkdownText` (the two heavy primitives the body composes) already live in `ui-primitives`, a dependency both packages already declare; the only genuinely host-specific pieces (`readFile`, `WorkspaceFileBrowseError` mapping, `workspaceId` resolution) stay caller-side, so extracting the pure body avoided ~90 duplicated lines with no coupling cost.
- **Have `apply.ts` call the store handle's own `.create(sessionId)` to reach bound actions from outside a component.** Rejected after tracing `SlotRegistry.resolveStore`: that call site's own cache is private to the renderer, so a second `.create()` call mints a disconnected instance, not the one `ConversationSession`/`ChatView` actually read — silently wrong, not merely inconvenient.
- **Make tab selection reactive to the registry instead of writing `conversationStore.view`** (resolve the active tab as `pendingFileOpen ?? storedView` at render time, no `setView` call at all). Rejected: it would add a second source of truth for "the active tab" alongside the existing persisted `view` field, diverging from the single-field design `inspect`/`chat`/`trajectory` already share, for no behavior difference once the registry-drain effect exists anyway.
- **Duplicate the `read` tool's classification (`viewerKindFor`/`langFromPath`) via import instead of a second local copy.** Rejected for the same reason `ui-workspace`'s own copy already rejected importing from `dsh-fs-tool-fs`: this is a small pure mapping, and `ui-conversation` importing `ui-workspace`'s copy would be the same forbidden cross-package symbol import as the rejected alternative above.

## Consequences

- `ConversationStoreState` gains `viewRequest: { view, focus } | null`, written by a generic `openView` action (a superset of the file-specific persisted field this note originally added); `ConversationSessionInjected` gains a `hooks.pendingFileOpen` compartment (`usePendingFileOpen` on the component side) that only `ConversationSession` consumes.
- `FilePreview`/`FilePreviewState`/`FilePreviewKind` are new public `ui-primitives` exports; `FileViewer.tsx`'s own `FileViewerProps`/behavior are unchanged from a caller's perspective (still a `Modal`, same footer/copy/external-open actions), so the sibling-browser note's existing behavior description of the *modal* stays accurate for the fallback path.
- `ConversationFileOpener` is a new optional `ctx` service (`ui-conversation` provides, anyone may `ctx.get`); `WorkspaceBrowserInjected` gains `openInConversation`, threaded through `WorkspaceBrowser`/`SessionTree`/`FilesNode` alongside the pre-existing `listWorkspaceEntries`/`readWorkspaceFile`/`openPath` props.
- `FileOpenRegistryImpl` never calls `forget(sessionId)` on session teardown — the same gap `ComposerBlockRegistry.forget` already has (declared, never invoked by any current caller); a per-session store leaks until the fiber unloads, unchanged in kind from the pre-existing registry this mirrors.
- Both `FilePreview` (`ui-primitives`) and every new `ui-conversation`/`ui-workspace` file this change touches reach 100% line/branch/function coverage in their own package suites; `ui-workspace/src/client/index.ts` and `WorkspaceBrowser.tsx` remain under the pre-existing GUI-debt coverage exemption (`vitest.config.ts`) that predates this change.
