# Agent Note: In-app file editing in the session File tab

Status: implemented

English | [中文](2026-08-27-file-tab-in-app-editing.zh.md)

## Problem

The session File tab ([File preview as a conversation tab](2026-08-26-file-preview-conversation-tab.md), later joined by a [View/Diff toggle](2026-08-27-file-tab-git-diff.md)) only ever previewed a file's content — every write to a workspace file still required leaving the app for an external editor. There was no write path from the browser UI at all: `workspace.readFile`/`gitStatus`/`gitCommitAll`/`gitDiscardAll` cover reading and git actions, but nothing lets the client overwrite a file's content, and no client package carried an embeddable text-editing surface (`ui-primitives` had `shiki`-based read-only highlighting only).

## Decision

**CodeMirror 6 as the editing surface, not Monaco.** Monaco (VS Code's engine) has long-standing weak touch/virtual-keyboard support and a multi-MB bundle with worker-based language services — a poor fit for a docked panel that must also run acceptably on lower-power/tablet hardware. CodeMirror 6 is modular, renders only visible lines, and composes from small maintained packages (`@codemirror/state`/`view`/`commands`, plus `@codemirror/lang-markdown` for Markdown's list/blockquote continuation) rather than needing a hand-rolled minimal setup.

**No per-language syntax highlighting while editing.** The app already has one syntax highlighter (`markdown/highlight.ts`, shiki-based, lazy-loaded per language) covering every `langFromPath` language for the read-only `ReadBlock`/`FilePreview` View mode. Wiring a second, CodeMirror-native grammar per language into the editing surface would duplicate that coverage — and its lazy-loaded bundle cost — for no reader-facing gain while typing. `FileEditor` (`ui-primitives`) is therefore an undecorated-monospace buffer; a user who wants highlighted code switches back to View. Markdown is the one exception: `kind: 'markdown'` splits into two columns, the buffer and a live preview pane re-rendering through the existing `MarkdownText` component on a 150ms debounce — a genuine live-preview editing surface built entirely from a component this package already had, not a new WYSIWYG dependency.

**`FileEditor` is uncontrolled after mount.** `path`/`text`/`kind` seed the initial buffer once; CodeMirror then owns the document, undo history, and cursor for that file's lifetime. `FileView` remounts it by keying on `path`, so switching files always gets a fresh buffer without `FileEditor` needing to reconcile external prop changes into a live CodeMirror `EditorState`.

**New `workspace.writeFile` RPC, built the same plain-`node:fs` way its siblings are, not through `dsh-fs`.** `workspace.readFile`/`gitStatus`/`gitCommitAll`/`gitDiscardAll` are all implemented in `packages/host/apiproxy` with plain `node:fs/promises` and `git` shell-outs (`workspace-files.ts`, `workspace-git.ts`); `dsh-fs`'s `FileSystem`/`writeText` capability is model-tool-facing only and was not wired into the apiproxy host process at all. Introducing it solely for this one write would cross an established package boundary for no shared benefit, so `writeWorkspaceFile` follows its siblings' existing precedent instead: it never creates a new file (the editor only opens files a prior read already resolved), and its write is atomic — a same-directory temp file, then `rename` — so a failure never leaves a partial file at the target path.

**Content hash, not mtime, for the write's staleness guard.** `readWorkspaceFile` computes a SHA-256 hex digest over the raw bytes it already reads and returns it as `version` on the `text` variant of `WorkspaceFileContent`; `writeWorkspaceFile` re-reads and re-hashes the current on-disk content immediately before writing, comparing against the caller's `expectedVersion`, and fails loud with the new `file-changed` business error code on a mismatch rather than silently overwriting a concurrent change (the agent editing the same file, another tab, an external editor). A content hash sidesteps filesystem mtime-resolution coarseness (some filesystems tick only per-second) that would make an mtime-based guard miss a same-second concurrent write. The check-then-write window between the hash comparison and the atomic publish is a narrow, accepted race, the same posture `workspace-git.ts`'s own write actions already take and document.

**A per-path in-memory draft cache in `FileView`, not native `beforeunload`/`confirm` dialogs.** `FileView` keeps a `Map<path, { text, version }>` (a plain ref, not React state — a keystroke only updates a reactive `hasDraft` boolean, not the whole tab) so switching to another file, or to View/Diff and back, never silently loses an edit; there is nothing to prompt-and-block because there is nothing to lose. This mirrors the composer's own per-session draft pattern (`inputHub`) rather than introducing a new unsaved-changes-guard mechanism. Saving clears the path's draft; a `file-changed` conflict surfaces an inline notice with a discard-and-reload action, since a stale draft's base is no longer valid to save over and there is no merge UI in v1.

**Scope: the docked File tab only, text and Markdown kinds only.** `ui-workspace`'s modal `FileViewer` fallback (used only when no session is current) does not gain editing — it is a secondary surface, and duplicating the wiring there for a rarely-hit path was not justified by a current consumer. Binary and image files offer no Edit toggle, the same scope line the Diff toggle already draws.

## Alternatives considered

- **Monaco Editor.** Rejected for the reasons above: touch support, bundle size, and worker overhead are worse fits for this docked, tablet-reachable panel than CodeMirror 6, and Monaco's markdown "language" is syntax highlighting only — it offers nothing CodeMirror doesn't already give for the live-preview feature that actually matters here.
- **CodeMirror-native syntax highlighting while editing** (a `@codemirror/lang-*`/`@codemirror/legacy-modes` package per `langFromPath` language, mirroring the read-only shiki coverage). Rejected: doubles the highlighting surface and its bundle cost for a purely cosmetic gain while typing, when View mode already renders the same file fully highlighted.
- **mtime-based staleness guard**, matching `dsh-fs`'s own `FsVersion`/`stat`-derived vocabulary more literally. Rejected: filesystem mtime resolution is not universally sub-second, so a same-second concurrent write could pass a stale check; a content hash is exact regardless of the underlying filesystem.
- **Wiring `dsh-fs`'s `writeText`/`FsWriteIntent` into the host apiproxy process** instead of a bespoke `writeWorkspaceFile`. Rejected: no other method in this process uses that capability seam, and adopting it for one write would mean constructing a `FileSystem` backend in a process that has never needed one, crossing a package boundary the sibling read/git methods deliberately do not cross.
- **A native `beforeunload`/`window.confirm` unsaved-changes guard.** Rejected: the per-path draft cache makes the guard unnecessary — nothing is ever lost by navigating away — and native dialogs are a worse UX than simply preserving the draft.
- **Editing the `ui-workspace` modal `FileViewer` too.** Deferred: no current consumer needs editing outside an active session, and duplicating the draft-cache/save-conflict wiring there without one would be speculative.

## Consequences

- `ui-primitives` gains four new dependencies (`@codemirror/state`, `@codemirror/view`, `@codemirror/commands`, `@codemirror/lang-markdown`) — each a small, independently maintained CodeMirror package, not a monolithic editor bundle.
- `WorkspaceApi`/`IWorkspaces` both widen (`writeFile`/`writeWorkspaceFile`), and `WorkspaceFileContent`'s `text` variant gains a required `version` field — every implementer (`host-apiproxy`'s real handler, `client/connection`'s fixture, `test-support/client-runtime`'s `TestWorkspaces` double, and the wire test doubles in `client/connection`/`client/runtime`'s `tests/`) gained the matching surface so the interfaces stay sound at compile time.
- A new `RpcErrorDetailsMap`/`rpcErrorSchema` code, `file-changed`, joins `file-too-large`/`directory-unreadable` as `workspace.writeFile`'s possible failures.
- The File tab's Edit mode is text/Markdown-only and offers no merge UI on conflict — both documented in `packages/host/apiproxy/README.md` and `packages/client/ui-conversation/README.md`'s Known Limitations.
- `workspace-files.ts`'s new `writeWorkspaceFile`/`hashContent`, the `workspace.writeFile` RPC handler (a real-composition test against a real temp-directory workspace, per `packages/CLAUDE.md`'s non-unit-test rule for product-visible plugins), `FileEditor`, and `FileView`'s edit-mode wiring all gained package-level test coverage; the real-composition test also covers the atomic write's no-partial-file guarantee under a forced write failure.
- No `apps/web/tests/snapshots/` browser scenario was added: the two prior File tab features in this same area (the preview tab and the View/Diff toggle) both shipped on package-level component coverage alone, with no web snapshot scenario of their own (their own Consequences sections cite only `FileView.client.spec.tsx`/`packages/CLAUDE.md`'s coverage posture) — this change follows that same precedent rather than introducing the first one. A `File` tab browser scenario (open a file, toggle Edit, type, save, verify the on-disk write) remains a plausible follow-up for whichever change first needs one.
