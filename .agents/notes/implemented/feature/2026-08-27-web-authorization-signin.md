# Agent Note: expose `ctx.authorization` over the RPC gateway for a web Sign-in affordance

Status: implemented

English | [中文](2026-08-27-web-authorization-signin.zh.md)

## Problem

`dsh --profile headless login <key>` ([2026-08-25-headless-authorization-login](2026-08-25-headless-authorization-login.md)) made `ctx.authorization` reachable from the CLI, but the web Settings page — where most users manage provider credentials — still offered only a single write-only API-key input (`packages/client/ui-settings-models/src/client/ProviderEditor.tsx`). A human with a Claude Pro/Max subscription and no wish to run a terminal command had no way to sign in through the product surface they were already using. That note's own "Alternatives considered" named this gap and deferred it, citing the missing gateway RPC surface, missing client UI, and the OAuth flow's local callback server (`127.0.0.1:53692`, opened by `@earendil-works/pi-ai`'s `loginAnthropic()`) being designed for the CLI's own machine rather than necessarily the browser's.

## Decision

**`begin()` acks the start, not the finish**, mirroring `session.prompt`'s `{accepted: true}` shape. `ctx.authorization.begin()` does not return until a human finishes clicking through an OAuth consent page — minutes, not milliseconds — so `POST /api/authorization.begin` (`packages/host/apiproxy/src/api-proxy.ts`) validates synchronously via `ctx.authorization.describe(key)` (unknown key/method or already-in-flight reject immediately with `authorization-not-found`/`authorization-in-flight`), then calls `ctx.authorization.begin()` without awaiting completion and returns immediately. Every notice, prompt, and settlement the attempt produces rides push state instead of this response.

**Notices and prompts ride the host stream, not the mux stream.** Authorization has no owning session, so its frames (`authorization/notice`, `authorization/prompt-requested`, `authorization/prompt-resolved`) join `HostFrame`, not `MuxFrame`. The prompt-requested/resolved pair is answerable exactly like `approval/requested`/`question/requested`: a stable `rpcId`, a `pendingAuthorizationPrompts` map, and a new `hostQueues` broadcast set (`host()` previously had no shared-broadcast counterpart to `mux()`'s `muxQueues`/`broadcast()` — added here) so every open Settings tab sees the same attempt. `respond()` gained a third routing branch alongside approvals and questions. `authorization/settled` (already emitted by the seam for every terminal outcome) needed no new frame type — it went straight into `API_REMOTE_FORWARDED_EVENTS` next to `credentials/reference-updated`, the existing verbatim-forwarding allowlist.

**State converges by key, not by caller.** The client never tracks "did my call start this attempt" — `AuthorizationRuntime` (`packages/client/runtime/src/client/authorization/`) keys all push state by `CredentialKey`, so a `begin()` call that loses a TOCTOU race against a concurrent call from another tab still renders the real (winning) attempt's notices and prompts correctly; the loser's `{accepted: true}` ack was only ever a lie about *starting* the flow, never about what the UI shows.

**`dsh-client-runtime` never calls `ctx.remote.$on`.** Nothing inside `packages/client/runtime/src/` subscribes to a Remote event; only feature packages built on top of the runtime do (`ui-settings-models` already bridges `credentials/reference-updated` this way, and `wire-events.client.spec.ts`'s fake `remote` service deliberately implements only `$dispatch`, documented as "this spec owns the carrier's handoff, not the fan-out behind it"). `authorization/settled` observance follows the same layering: `IAuthorization` exposes a plain `notifySettled(key)` method rather than subscribing itself, and `ui-settings-models/src/client/index.ts`'s existing pushed-invalidations effect calls it from its own `ctx.remote.$on('authorization/settled', ...)`.

**`AuthorizationPanel` is generic**, carrying no Anthropic/OAuth/pi-ai-specific code: it renders `AuthorizationNotice`/`AuthorizationPrompt` by shape (`message`/`url`/`code`; `text`/`secret`/`select`), exactly the posture `dsh-authorization`'s own module doc states ("a surface that renders one flow renders all of them"). `ProviderEditor` decides whether to show it per row by checking whether `ctx.authorization`'s loaded entry list contains a `CredentialKey` matching `${namespace.ns}/${provider}` (string comparison against the branded key — `dsh-credentials`'s constructor lives in its service-bearing `index.ts`, and `types.ts` stays runtime-code-free by convention, so no browser-safe constructor exists to call instead) — never a `layout === 'pi-ai'` family check, so a route the catalog registers no flow for (DeepSeek, most hand-declared pi-ai routes) shows nothing extra with no per-family branching to maintain.

**No auto-cancel on panel close.** Closing the Settings dialog mid-flow does not call `authorization.cancel()`. The shared per-key push state is exactly what makes this safe: a human who opens the `auth_url` link in a new tab and closes Settings to wait keeps their attempt running, and reopening the row (or another tab entirely) picks the same live state back up via the host stream's reconnect replay of still-pending prompts. Cancellation is only ever the explicit button inside `AuthorizationPanel`.

**`Omit<AuthorizationPrompt, 'signal'>` is not what it looks like.** TypeScript's built-in `Omit` applied to a union collapses it into one flattened object type, discarding `kind`-based narrowing — `prompt.kind === 'select'` would stop seeing `options`. `packages/host/apiproxy/src/api/authorization.ts` exports `WireAuthorizationPrompt` via a `DistributiveOmit<T, K> = T extends unknown ? Omit<T, K> : never` instead, threaded through the wire type, `HostFrame`, and the client-runtime contract in place of every ad hoc `Omit<AuthorizationPrompt, 'signal'>`.

**`dsh-authorization`'s `authorization/settled` `Events` declaration moved from `index.ts` to `types.ts`.** It was declared alongside the `Context.authorization` merge, both in the cordis-bearing `index.ts` — but `dsh-credentials`' own `credentials/reference-updated`/`credentials/record-updated` split this exact way (`Events` in `types.ts`, `Context` in `index.ts`) specifically so a browser-safe consumer can pull in the event's declared shape via `import type {} from '.../types'` without loading the service-bearing half. `authorization/settled` needed the same split to reach `API_REMOTE_FORWARDED_EVENTS`' shape-gate assertion in `packages/api/remotes/src/index.ts`.

## Alternatives considered

- **Threading `Pick<IApiClient, 'authorization' | 'respond'>` into `AuthorizationPanel`** instead of the higher-level `IAuthorization` client-runtime service — rejected once `AuthorizationRuntime` existed, since it already handles `rpcId` bookkeeping (`respondPrompt(rpcId, answer)` vs. hand-building a `ClientResponse` envelope) and shared per-key state; using the raw wire face would have duplicated both.
- **Requiring `authorization` on every `ProviderEditor` caller** (matching how `api` is required) — rejected: `DeepSeekOnboardingDialog`'s credential-only onboarding step has no use for subscription sign-in, and DeepSeek registers no flow regardless. `ProviderEditorProps.authorization` is optional; only `ModelsSectionInjected.authorization` (the caller that needs it) is required.
- **Auto-cancelling the attempt when `AuthorizationPanel` unmounts** — closing the panel felt like it should stop an attempt nobody is watching, but the reconnect-safe shared-state design makes that wrong: a human who opens the OAuth link in a new tab and closes Settings to wait would have their in-progress login killed the instant the dialog closed. Cancellation is only ever the explicit button.

## Consequences

Every profile mounting `dsh-authorization` (all of `dsh-base`'s derivatives, per the prior note) now also exposes it over the RPC gateway whenever `dsh-host-apiproxy` is composed — dormant until a caller `begin()`s, same posture as the CLI path. `dsh-authorization`'s package boundary shifted: `Events` declarations live in `types.ts` going forward, matching `dsh-credentials`'s precedent, so a future event added to that seam should follow the same split rather than landing in `index.ts`.

A browser and the harness host on different machines still cannot complete the callback-server half of pi-ai's Anthropic OAuth race automatically — `loginAnthropic()`'s own `auth_url` notice already anticipates this with a "paste the redirect URL" fallback prompt, which `AuthorizationPanel` renders as an ordinary `text` prompt with no special-casing.

## Testing

New `packages/host/apiproxy/tests/api-proxy-authorization.spec.ts` follows the sibling `api-proxy-approval.spec.ts`/`api-proxy-question.spec.ts` per-domain file pattern: a real `AuthorizationService` + a local in-memory `CredentialProvider` double (a near-duplicate of `packages/credentials/authorization/tests/memory.ts`'s own `MemoryCredentials`, which already anticipated a third copy), a test-only committing `AuthorizationFlow`, no real OAuth network call. Covers `list`/`begin` rejections, the notice/prompt-requested/prompt-resolved/settled sequence, `respond` answering and declining, `cancel`, and host-stream reconnect replay of a still-pending prompt. `client-handler.spec.ts`'s existing config-unary-surface round-trip test gained the three authorization methods for the client-carrier half (`AbstractApiClient`/`toFetchHandler`'s dispatch tables), which the domain test alone does not exercise.

New `packages/client/runtime/tests/authorization-service.client.spec.ts` covers `AuthorizationManager` (refresh/seeding, all three host-frame types, begin/cancel/respond/decline wire calls, settlement) and `AuthorizationRuntime`'s thin delegation + `ctx.reflect.provide` registration. Writing it surfaced a real bug: `declinePrompt` was missing the same-rpcId-still-pending guard `respondPrompt` already had, so a stale or double decline click would have sent a wire call for a prompt already answered; fixed to match.

`packages/client/ui-settings-models/tests/` gained `authorization-panel.client.spec.tsx` (method choice, all three prompt kinds, decline/cancel, both begin() and respondPrompt() failure paths including non-`Error` rejections) and `provider-editor-authorization.client.spec.tsx` (the lazy `refreshEntries()` trigger, and the affordance's data-driven visibility for a matching vs. non-matching row). Writing the select-prompt test surfaced a second real bug: the select option's `onClick` called `setDraft(option.id)` then immediately read the still-stale `draft` closure variable in the same tick (React state updates are not synchronous), sending an empty answer instead of the chosen option's id; fixed by having `submitPrompt` take the answer as an explicit parameter instead of reading component state. Every existing `ModelsSection`/`ProviderEditor` test fixture across `provider-form.client.spec.tsx`, `components.client.spec.tsx`, and `apply.client.spec.ts` needed a `TestAuthorization` double (new: `packages/test-support/client-runtime/src/authorization.ts`, mirroring the existing `TestWorkspaces` shape) once `authorization` became a required prop/inject; defaults to `state: 'loaded'` with no entries so unrelated tests see no Sign-in affordance and no background refresh.

Per-file 100% coverage (`pnpm run test:coverage`'s gate) holds for every new and changed file in these packages, confirmed by scoped `vitest --coverage` runs. One coverage-tooling gap surfaced during this work is pre-existing and unrelated: `packages/client/runtime`'s vitest lane reports 0/0 covered lines for `--coverage.include` scoped to that package in this sandbox, reproduced identically against an untouched existing file (`workspaces-service.client.spec.ts`) — a sandbox/lane quirk, not a gap this change introduced.
