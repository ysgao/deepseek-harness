# Agent Note: expose `ctx.authorization` over the RPC gateway for a web Sign-in affordance

Status: implemented

English | [中文](2026-08-27-web-authorization-signin.zh.md)

## Problem

`dsh --profile headless login <key>` ([2026-08-25-headless-authorization-login](2026-08-25-headless-authorization-login.md)) made `ctx.authorization` reachable from the CLI, but the web Settings page — where most users manage provider credentials — still offered only a single write-only API-key input (`packages/client/ui-settings-models/src/client/ProviderEditor.tsx`). A human with a Claude Pro/Max subscription and no wish to run a terminal command had no way to sign in through the product surface they were already using. That note's own "Alternatives considered" named this gap and deferred it, citing the missing gateway RPC surface, missing client UI, and the OAuth flow's local callback server (`127.0.0.1:53692`, opened by `@earendil-works/pi-ai`'s `loginAnthropic()`) being designed for the CLI's own machine rather than necessarily the browser's.

## Decision

**`begin()` is one long-lived Remote call, not an ack-then-push split.** `AuthorizationController` (`packages/api/settings-controller/src/authorization.ts`, the Host owner of the generated `ctx.remote.authorization` namespace) declares `begin` as an ordinary `@Remote` method that `await`s `ctx.authorization.begin()` for as long as a human takes to click through an OAuth consent page — minutes, not milliseconds — and returns the real `AuthorizationOutcome` (`authorized`/`cancelled`) once it settles. Typert's Remote transport keeps a call open that long natively, so there is no separate synchronous-ack step; unknown key/method or an already-running attempt surface as a thrown `AuthorizationError`, mapped by `failure()` to `authorization-not-found`/`authorization-in-flight`/`authorization-rejected`.

**Notices and prompts ride a dedicated stream, not `begin`'s own return.** `AuthorizationController.follow` is a `@Remote({ mode: 'stream' })` method backed by `AuthorizationFeed`/`AuthorizationFollower` (mirroring `WorkspaceController`'s `WorkspaceFeed`/`WorkspaceFollower` reconnect-baseline pattern): each new `follow()` generation first replays every still-pending prompt, then streams live `notice`/`prompt-requested`/`prompt-resolved` frames, so every open Settings tab sees the same attempt regardless of which tab called `begin`. `respond(key, answer)` answers whichever prompt is pending for that key from any connected tab. `authorization/settled` (already emitted by the seam for every terminal outcome) needed no bespoke wiring — it rides `API_REMOTE_FORWARDED_EVENTS` (`packages/api/remotes/src/{index.ts,types.ts,remote-events.ts}`) next to `credentials/reference-updated`, the existing verbatim-forwarding allowlist.

**State converges by key, not by caller.** The client never tracks "did my call start this attempt" — `AuthorizationRuntime` (`packages/client/ui-settings-models/src/client/authorization-runtime.ts`) keys all push state by `CredentialKey`, so a `begin()` call that loses a TOCTOU race against a concurrent call from another tab still renders the real (winning) attempt's notices and prompts correctly; a losing caller's own `begin()` promise settles with whatever the winning attempt actually produced, since both calls converge on the same underlying flow.

**The authorization client runtime has no shared cross-package facade.** Unlike Workspace or Session, `ui-settings-models` is `AuthorizationRuntime`'s sole consumer, so the state lives directly in that package next to the UI reading it, rather than in a separate `dsh-api-*-controller/client` package. `IAuthorization` exposes a plain `notifySettled(key)` method rather than subscribing to the event itself, and `ui-settings-models/src/client/index.ts`'s own pushed-invalidations effect calls it from its own `ctx.remote.$on('authorization/settled', (key) => { ctx.authorization.notifySettled(key) })` — the same bridging pattern that package already used for `credentials/reference-updated`.

**`AuthorizationPanel` is generic**, carrying no Anthropic/OAuth/pi-ai-specific code: it renders `AuthorizationNotice`/`AuthorizationPrompt` by shape (`message`/`url`/`code`; `text`/`secret`/`select`), exactly the posture `dsh-authorization`'s own module doc states ("a surface that renders one flow renders all of them"). `ProviderEditor` decides whether to show it per row by checking whether `ctx.authorization`'s loaded entry list contains a `CredentialKey` matching `${namespace.ns}/${provider}` (string comparison against the branded key — `dsh-credentials`'s constructor lives in its service-bearing `index.ts`, and `types.ts` stays runtime-code-free by convention, so no browser-safe constructor exists to call instead) — never a `layout === 'pi-ai'` family check, so a route the catalog registers no flow for (DeepSeek, most hand-declared pi-ai routes) shows nothing extra with no per-family branching to maintain.

**No auto-cancel on panel close.** Closing the Settings dialog mid-flow does not call `authorization.cancel()`. The shared per-key push state is exactly what makes this safe: a human who opens the `auth_url` link in a new tab and closes Settings to wait keeps their attempt running, and reopening the row (or another tab entirely) picks the same live state back up via the host stream's reconnect replay of still-pending prompts. Cancellation is only ever the explicit button inside `AuthorizationPanel`.

**`Omit<AuthorizationPrompt, 'signal'>` is not what it looks like.** TypeScript's built-in `Omit` applied to a union collapses it into one flattened object type, discarding `kind`-based narrowing — `prompt.kind === 'select'` would stop seeing `options`. `packages/api/settings-controller/src/types.ts` exports `WireAuthorizationPrompt` via a `DistributiveOmit<T, K> = T extends unknown ? Omit<T, K> : never` instead, threaded through the wire type, `AuthorizationStreamFrame`, and the client-runtime contract in place of every ad hoc `Omit<AuthorizationPrompt, 'signal'>`.

**`dsh-authorization`'s `authorization/settled` `Events` declaration lives in `types.ts`, not `index.ts`.** `dsh-credentials`' own `credentials/reference-updated`/`credentials/record-updated` split this way (`Events` in `types.ts`, `Context` in `index.ts`) specifically so a browser-safe consumer can pull in the event's declared shape via `import type {} from '.../types'` without loading the service-bearing half; `authorization/settled` follows the same split to reach `API_REMOTE_FORWARDED_EVENTS`'s shape-gate assertion in `packages/api/remotes/src/index.ts`.

## Alternatives considered

- **Threading the raw `ctx.remote.authorization` face into `AuthorizationPanel`** instead of the higher-level `IAuthorization` client-runtime service — rejected once `AuthorizationRuntime` existed, since it already handles the `follow`-stream pump and shared per-key state; using the raw Remote face directly would have duplicated both.
- **Requiring `authorization` on every `ProviderEditor` caller** (matching how `api` is required) — rejected: `DeepSeekOnboardingDialog`'s credential-only onboarding step has no use for subscription sign-in, and DeepSeek registers no flow regardless. `ProviderEditorProps.authorization` is optional; only `ModelsSectionInjected.authorization` (the caller that needs it) is required.
- **Auto-cancelling the attempt when `AuthorizationPanel` unmounts** — closing the panel felt like it should stop an attempt nobody is watching, but the reconnect-safe shared-state design makes that wrong: a human who opens the OAuth link in a new tab and closes Settings to wait would have their in-progress login killed the instant the dialog closed. Cancellation is only ever the explicit button.

## Consequences

Every profile mounting `dsh-authorization` (all of `dsh-base`'s derivatives, per the prior note) now also exposes it over the RPC gateway whenever `@deepseek-ai/dsh-api-settings-controller` is composed — dormant until a caller `begin()`s, same posture as the CLI path. `dsh-authorization`'s package boundary shifted: `Events` declarations live in `types.ts` going forward, matching `dsh-credentials`'s precedent, so a future event added to that seam should follow the same split rather than landing in `index.ts`.

A browser and the harness host on different machines still cannot complete the callback-server half of pi-ai's Anthropic OAuth race automatically — `loginAnthropic()`'s own `auth_url` notice already anticipates this with a "paste the redirect URL" fallback prompt, which `AuthorizationPanel` renders as an ordinary `text` prompt with no special-casing.

## Testing

`packages/api/settings-controller/tests/authorization.host.spec.ts` covers `AuthorizationController` end to end against a real `AuthorizationService` and a test-only committing `AuthorizationFlow`, no real OAuth network call: `list`/`begin` rejections (`authorization-not-found`/`authorization-in-flight`/`authorization-rejected`), the notice/prompt-requested/prompt-resolved/settled sequence over `follow`, `respond` answering and declining, `cancel`, and reconnect replay of a still-pending prompt to a new `follow()` generation. The generic client-carrier dispatch machinery (what `client-handler.spec.ts`'s round-trip test used to cover per-domain) is now `dsh-api-gateway`'s own test suite, exercised once for every Remote namespace rather than per domain.

`packages/client/ui-settings-models/src/client/authorization-runtime.ts`'s `AuthorizationRuntime` — the single class that now does what a separate `AuthorizationManager`/`AuthorizationRuntime` split used to (there is no shared cross-package client-runtime package for this feature to split across) — is exercised through the package's own `apply.client.spec.ts` and the panel/editor specs below rather than a dedicated unit spec, since its `follow`-stream pump and per-key state have no meaningful behavior apart from the UI that reads them.

`packages/client/ui-settings-models/tests/` has `authorization-panel.client.spec.tsx` (method choice, all three prompt kinds, decline/cancel, both begin() and respondPrompt() failure paths including non-`Error` rejections) and `provider-editor-authorization.client.spec.tsx` (the lazy `refreshEntries()` trigger, and the affordance's data-driven visibility for a matching vs. non-matching row). Writing the select-prompt test surfaced a real bug: the select option's `onClick` called `setDraft(option.id)` then immediately read the still-stale `draft` closure variable in the same tick (React state updates are not synchronous), sending an empty answer instead of the chosen option's id; fixed by having `submitPrompt` take the answer as an explicit parameter instead of reading component state. Every existing `ModelsSection`/`ProviderEditor` test fixture across `provider-form.client.spec.tsx`, `components.client.spec.tsx`, and `apply.client.spec.ts` needed a `TestAuthorization` double (`packages/client/ui-settings-models/tests/test-authorization.client.ts`, mirroring the shape `TestWorkspaces` used before that fixture package was dissolved) once `authorization` became a required prop/inject; defaults to `state: 'loaded'` with no entries so unrelated tests see no Sign-in affordance and no background refresh.

Per-file 100% coverage (`pnpm run test:coverage`'s gate) holds for every file in this feature. `failure()`'s `AuthorizationError` branch handling documents, rather than tests around, one genuinely unreachable path: `dsh-authorization`'s own `begin()` never lets a declined prompt reach a caller as a thrown `AuthorizationDeclinedError` — it observes the decline itself and settles `begin()` as `{ status: 'cancelled' }` instead — so `failure()` only ever needs to map the seam's own `NO_FLOW`/`ALREADY_IN_FLIGHT` refusals plus a generic fallback.
