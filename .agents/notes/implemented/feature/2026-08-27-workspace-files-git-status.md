# Agent Note: Workspace Files tree shows git branch and per-file status

Status: implemented

English | [中文](2026-08-27-workspace-files-git-status.zh.md)

## Problem

The Workspace Files tree ([sibling-browser Agent Note](2026-08-24-workspace-files-sibling-browser.md)) lists directories and files but carries no git awareness: a user browsing a git-tracked workspace cannot see the current branch or which files have pending changes without leaving the app. `workspace.listEntries`/`workspace.readFile` already establish the pattern for a Files-tree-only host primitive (`files.ts`, unsandboxed, direct `node:fs/promises` calls); git status needed the same shape of addition.

## Decision

**A third `workspace.gitStatus({ workspaceId })` RPC method, built end-to-end on the `listEntries`/`readFile` template.** It follows the same `@Remote`-method pattern those two already use on `WorkspaceController` (`packages/api/workspace-controller/src/index.ts`): a `WorkspaceGitStatus` type and error codes in `types.ts`, a `@Remote('gitStatus')` method that resolves the workspace and delegates to a new host primitive, `workspaceGitStatus` in `workspace-git.ts`. Unlike `listEntries`/`readFile`, the request carries no `path` — git status is scanned once for the whole repository, not per browsed directory (see alternatives).

**`workspace-git.ts` shells out to the host's own `git` binary** via `node:child_process.execFile` (promisified), the same "direct Node primitive, no capability-seam indirection" posture `workspace-files.ts` already established for this host-native, unsandboxed surface. Three git invocations: `rev-parse --show-toplevel` resolves the enclosing repository root (which may be an ancestor of the workspace's own directory — a workspace need not be a repo root); `symbolic-ref --short HEAD` reads the branch name; `status --porcelain=v1 -z --untracked-files=all` reads pending changes. A directory outside any git working tree, or a host missing the `git` binary entirely, both resolve as `{ isRepo: false, branch: null, files: {} }` — a normal result, not a business error; the module never distinguishes "not a repo" from "can't tell."

`-z` (NUL-terminated, never-quoted porcelain output) is deliberate: the default LF-terminated form C-style-quotes any path containing a byte ≥ 0x80 under git's default `core.quotePath=true`, octal-escaping non-ASCII bytes rather than emitting them as text — a real correctness bug for a bilingual (`zh`/`en`) product where Chinese filenames are ordinary input, not an edge case. `-z` reports every path verbatim; a rename/copy record becomes two consecutive NUL-terminated fields (new path, then original path), and only the new path — what the tree currently shows — is kept. Each porcelain `XY` pair collapses to one display letter (`M`/`A`/`D`/`R`/`C`, or `U` for `??` untracked): the staged (index) letter when set, else the worktree letter.

**Branch name uses `symbolic-ref --short HEAD`, not `rev-parse --abbrev-ref HEAD`.** The latter fails on an unborn branch (a freshly `git init`-ed repository with no commits yet — a real, common state, not exotic) because it has no commit to resolve; `symbolic-ref` reads HEAD's ref target directly and resolves in both cases. A detached HEAD (points at a commit, not a ref) has no branch name and reports as the literal `"HEAD"`, git's own convention.

**Client and UI threading mirrors the sibling props exactly.** `IWorkspaces` gains `listWorkspaceGitStatus`, `commitAllWorkspaceChanges`, `discardAllWorkspaceChanges`; `ClientWorkspaceModel` (`packages/api/workspace-controller/src/client/model.ts`) implements each as a thin `this.remote.{gitStatus,gitCommitAll,gitDiscardAll}(...)` call; `WorkspaceBrowserInjected`/`WorkspaceBrowser`/`SessionTree`/`FilesNodeProps` each gain the matching props alongside `listWorkspaceEntries`/`readWorkspaceFile`. `FilesNode` fetches git status on mount (and on `workspaceId` change), aborting on unmount. The always-visible header row (not gated on the tree's own internal expand toggle) shows the branch name and, once `files` is non-empty, a changed-file-count badge (`.gitChangedCount`) plus Commit-all/Discard-all icon buttons; each file row shows its status letter, color-coded via the existing `--dsw-alias-state-{warn,success,error,business}-primary` tokens, after the file name. A directory row's own aggregate marker still uses `StateDot` (see below).

**Git status has no live push channel, so it has two pull-refresh routes instead: an explicit refresh icon in the header, and toggling the Files tree closed then open** (the same "collapse-then-reopen refetches" lifecycle `useLevel`'s directory-listing hook already has, and it composes for free here since `FilesNode`'s own expand handler already runs on every toggle). `useGitStatus` returns `[status, refresh]`; `refresh` bumps a token in the fetch effect's dependency array without clearing the current `status` first, so a refresh updates the display in place rather than blanking it — unlike a `workspaceId` change, which does clear it (a different workspace's stale status must not linger). The refresh button sits as a flex sibling of the expand-toggle `<button>`, not nested inside it — `<button>` inside `<button>` is invalid HTML and double-fires the wrong handler — so the header's outer element is a plain `<div>` (`.headerRow`) with the toggle button (`.headerToggle`, `flex: 1`) and `GitStatusSummary` (branch, dirty dot, refresh button) as two flex children.

`TestWorkspaces` (`test-support/client-runtime`) and the package's own `WorkspaceRemote` wire test doubles (`packages/api/workspace-controller/tests/{transport,model}.client.spec.ts`) both implement the new method — recording the call and defaulting to `isRepo: false`, since none of these test doubles model a real git working tree.

**A directory row also carries an aggregate dirty marker**, shown when any file under it — at any depth, whether or not that level has ever been fetched — has a pending change. Because `files` already covers the whole repository from one fetch, a directory row answers this with a plain prefix scan over that same map (`isUnderDirectory`, path-segment-boundary-checked so `/ws/foo` does not falsely match `/ws/foobar/x.txt`) rather than a second request; walking into an unexpanded subtree needed no separate signal to know it holds a change.

**Two more RPC methods, `workspace.gitCommitAll({ workspaceId, message })` and `workspace.gitDiscardAll({ workspaceId })`, complete the same `@Remote`-method template as `gitStatus`.** Both delegate to new `workspace-git.ts` functions, `commitAllChanges` and `discardAllChanges`, which shell out to `git` the same way `workspaceGitStatus` does. `commitAllChanges` runs `git add -A` then `git commit -m <message>` (a blank/whitespace-only message is rejected by the request schema's `.refine()`, not by the host primitive). `discardAllChanges` runs `git reset` then `git checkout -- .` as two sequential commands, never `git restore --staged --worktree --source=HEAD -- .` in one call — a manual repro confirmed the latter deletes a staged-but-uncommitted new file outright, since `git restore` resolves "restore to HEAD" for a staged addition as "this path did not exist at HEAD" and removes it; `reset` un-stages without touching the worktree, then `checkout -- .` reverts only tracked worktree content, leaving untracked files (staged or not) alone. **Discard is therefore tracked-changes-only, never a full clean** — `discardAllChanges` never runs `git clean` (see alternatives).

**Unlike `gitStatus`, `gitCommitAll`/`gitDiscardAll` treat "not a repository" as a business error, not a normal result.** `gitStatus`'s `{ isRepo: false }` return lets the header quietly render nothing; committing or discarding is a deliberate user action with no meaningful outcome outside a working tree, so `workspace-git.ts` throws `GitNotARepositoryError` instead, and any other git failure (a failing hook, a merge conflict, a missing `git` binary at commit time) surfaces as `GitCommandError` carrying the failing subcommand's name. Both map to new `WorkspaceErrorDetailsMap` entries, `git-not-a-repository` and `git-command-failed`. Both new RPC calls take a caller-provided `signal: AbortSignal` and impose no separate deadline of their own, since a commit can invoke an arbitrarily slow pre-commit/commit-msg hook and should run to completion (or the user's own cancellation) rather than time out under a budget picked for ordinary read calls.

**The commit message is an inline text field (`GitCommitInput`) that replaces the branch/badge row in place while active, not a modal.** Enter submits (once the trimmed message is non-blank and no request is pending), Escape cancels, and a Check/Close icon pair offers the same two actions by click. Discard, being destructive and needing no free-text input, instead opens a confirmation `Modal` naming the exact tracked-vs-untracked scope before it runs.

**Commit and Discard are icon-only buttons** — `IconArrowUpOutline14` (an up arrow into a base line) and `IconUndoOutline14` (a shaft hooking back on itself) — both newly hand-drawn, stroke-based additions to `ui-primitives`'s icon set; neither has a Figma source, following the set's existing "drawn placeholder" precedent rather than a deepsuite/figma extraction. Their `title` attribute (`files.git.commit`/`files.git.discard`) is the only label, matching the header's icon-only refresh button. A successful commit or discard bumps `levelRefreshKey`, remounting the currently expanded `FilesLevel` (and everything nested under it) so the tree's own directory listing picks up the changed file content — neither action has another channel to tell an already-fetched level that files on disk changed.

## Alternatives considered

- **A bundled JS git implementation (`isomorphic-git`, `simple-git`) instead of shelling out.** Rejected: the "prefer maintained dependencies over hand-rolling" policy applies when a dependency deletes owned code; here the owned code is a few git subprocess calls and porcelain parsing, well inside what `workspace-files.ts` already does with raw `node:fs` for the same surface, and the host running this GUI already requires `git` to exist for the workspace to be useful at all.
- **Default LF-terminated `--porcelain=v1` with C-style quote/octal-escape parsing.** Rejected after confirming (a manual repro with a `你好.txt` file) that git's default `core.quotePath=true` octal-escapes non-ASCII path bytes rather than emitting them as text — a real corruption bug for Chinese filenames, not a hypothetical. `-z` sidesteps quoting entirely; no unquoting logic is needed.
- **`git rev-parse --abbrev-ref HEAD` for the branch name.** Rejected: fails outright on a fresh `git init`-ed repository with no commits (unborn HEAD) — caught by a test using exactly that state. `symbolic-ref --short HEAD` resolves an unborn branch the same as one with history.
- **Scoping the git status call to the currently browsed subdirectory (`git status <path>`).** Rejected: the Files tree can expand to any nested directory independently, and status badges at every depth must be correct from one header-level fetch rather than a re-fetch per expanded directory; scanning the whole repository from its root and keying the result by absolute path serves every level uniformly.
- **Reusing `packages/fs` or `packages/subprocess` instead of a direct `node:child_process` call.** Rejected: `packages/fs` is the model-tool filesystem capability (sandboxed agent read/write tools) and `packages/subprocess` is the full agent-tool subprocess seam (stdio dispositions, credential scrubbing, tree-scoped signal escalation) — both built for a different consumer than this host-native, unsandboxed Web GUI surface, which `workspace-files.ts` already established calls Node primitives directly.
- **A directory row's aggregate marker carries its own status letter** (mirroring the file-row badge) rather than a plain dirty dot. Rejected: a folder can contain a mix of added, modified, and deleted descendants at once, and picking one letter to represent that mix would misrepresent the other kinds present; a dot only claims "something changed inside," which is always true when shown.
- **A second, folder-scoped RPC call (or a client-side recursive fetch) to answer "does this directory contain changes?"** Rejected: the repository-wide `files` map already answers this with a plain prefix scan (`isUnderDirectory`) over data already in hand — a directory row needed no additional fetch, aggregation query, or eager expansion of unfetched levels.
- **A live push channel** (an SSE/watch-based `host/workspace-git-changed` frame, mirroring `host/workspace-changed`) instead of pull-refresh. Rejected as disproportionate: git status can change from outside the app at any time (another terminal, another tool), so a push channel would need a filesystem watcher on `.git` per open workspace, running continuously, for a panel that is not the primary view. Two cheap, user-initiated pull routes (explicit refresh, collapse-then-reopen) cover the same need without that standing cost.
- **Clearing `status` to `undefined` at the start of every refresh**, matching the original once-per-mount fetch's own reset. Rejected once it was actually wired to a manual refresh: it made the branch label and badges flash empty on every click before the new result arrived, for data that is usually still current. Only a `workspaceId` change now clears eagerly; a same-workspace refresh keeps the last known value in view until the new one lands.
- **`git restore --staged --worktree --source=HEAD -- .` as Discard's single command.** Rejected after a manual repro showed it deletes a staged-but-uncommitted new file outright rather than merely un-staging it. `git reset` (un-stage only) followed by `git checkout -- .` (revert tracked worktree content only) achieves the same net effect for genuinely tracked changes without that data loss.
- **A full `git clean -fd` as part of Discard**, treating "discard all" as "reset the worktree to a clean checkout." Rejected via `AskUserQuestion`, confirmed explicitly before implementing: an untracked file has no committed content to fall back to, so "discarding" it can only mean deleting it outright — a materially more destructive action than reverting a tracked edit (which git can always recreate from `HEAD`), and one a user clicking "Discard all" on a *files* panel would not expect from that label.
- **A modal dialog for the commit message**, mirroring the discard confirmation's own `Modal`. Rejected via `AskUserQuestion` in favor of an inline field: one line of free text does not need a modal's focus-trap weight, and replacing the branch/badge row in place keeps the header at its usual one-row height instead of opening a second surface for a single input.

## Consequences

- New files: `packages/api/workspace-controller/src/workspace-git.ts`, its test `packages/api/workspace-controller/tests/workspace-git.host.spec.ts`.
- New RPC method `workspace.gitStatus`, request `{ workspaceId }`, response `WorkspaceGitStatus { isRepo, branch, files }` — a normal (non-error) `isRepo: false` result covers both "not a repository" and "no `git` binary available."
- Two more RPC methods: `workspace.gitCommitAll`, request `{ workspaceId, message }` (rejects a blank/whitespace message at the schema layer), and `workspace.gitDiscardAll`, request `{ workspaceId }` — both `void`-valued on success, both throwing `git-not-a-repository`/`git-command-failed` (new `WorkspaceErrorDetailsMap` entries) rather than returning a normal result outside a working tree.
- `IWorkspaces`, `WorkspaceBrowserInjected`, and `FilesNodeProps` each gain `listWorkspaceGitStatus` plus `commitAllWorkspaceChanges`/`discardAllWorkspaceChanges` (`commitAllChanges`/`discardAllChanges` on `FilesNodeProps`); `TestWorkspaces` and the package's own `WorkspaceRemote` wire test doubles implement all three, none modeling a real git working tree, so commit/discard resolve through the same `git-not-a-repository` error path `gitStatus` uses for `isRepo: false`.
- Two new hand-drawn icons in `ui-primitives`: `IconArrowUpOutline14`, `IconUndoOutline14` (no Figma source); the icon-set regression test's hardcoded total moved from 71 to 73.
- New locale keys `files.git.branch`, `files.git.changedCount`, `files.git.folderDirty`, `files.git.refresh`, `files.git.commit`, `files.git.discard`, `files.git.commitPlaceholder`, `files.git.commitSubmit`, `files.git.cancel`, `files.git.discardConfirmTitle`, `files.git.discardConfirmDesc`, `files.git.discardConfirm`, `files.git.discardPending`, `files.git.status.{M,A,D,R,C,U}` in both `zh` and `en`; `files.git.dirty` was retired once the header's dirty dot was replaced by the changed-count badge.
- Every touched file reaches 100% line/branch/function coverage in its own package suite (`workspace-git.ts` — 18 tests covering `gitStatus`/`commitAllChanges`/`discardAllChanges`; `FilesNode.tsx` — 36 tests; the `WorkspaceController`/client `model.ts`/`service.ts` wiring); one branch in `workspace-git.ts` — an abort landing in the narrow window between a git subprocess call settling and the next one starting — is `v8 ignore`d per subcommand as not portably raceable in a test, the same precedent `workspace-files.ts` already sets for its own mid-scan-failure branch. `ui-workspace/src/client/index.ts` and `WorkspaceBrowser.tsx` remain under the pre-existing GUI-debt coverage exemption (`vitest.config.ts`) that predates this change; the prop threading added there carries no new branches.
- An earlier draft let a caller-signal abort during the repository-root check collapse into the ordinary `isRepo: false` result (the `catch` swallowed everything, abort included) — caught by a test and fixed before landing: an abort now rethrows and propagates to the RPC handler's `cancelled` response, matching how `listEntries`/`readFile` already report cancellation.
