# Agent Note: Workspace Files tree gets git Pull (rebase) and Push

Status: implemented

English | [中文](2026-08-28-workspace-files-git-pull-push.zh.md)

## Problem

The Files tree's git toolbar ([git-status Agent Note](2026-08-27-workspace-files-git-status.md)) already shows branch/status and offers Commit-all/Discard-all, but a user with a configured remote had no way to sync with it from inside the app — pulling or pushing meant leaving for a terminal.

## Decision

**Two more RPC methods, `workspace.gitPullRebase({ workspaceId })` and `workspace.gitPush({ workspaceId })`, complete the same six-layer template `gitStatus`/`gitCommitAll`/`gitDiscardAll` already established.** Both delegate to new `workspace-git.ts` functions, `pullRebase` and `push`, which resolve the repository root the same way the write actions do (`repoRootOrThrow`, throwing `GitNotARepositoryError` rather than quietly no-opping — a sync the caller believes succeeded must not silently fail). `pullRebase` shells out to `git pull --rebase` with no extra arguments: it acts on the current branch and its already-configured upstream, with no override surface. `push` resolves the branch's configured remote (`branch.<name>.remote`) and pushes an explicit `<remote> HEAD` refspec rather than a bare `git push` — a bare push's scope depends on the host's `push.default`/`remote.<name>.push` configuration (e.g. `push.default: matching` can also push every other locally-diverged branch with a same-named remote counterpart), which would silently widen "Push" beyond the current branch on a host configured that way; a branch with no configured remote falls back to a bare `git push`, reporting the same "no configured push destination" failure either way. A failing command throws `GitCommandError('pull', …)`/`GitCommandError('push', …)`, reusing the existing `git-not-a-repository`/`git-command-failed` `RpcErrorDetailsMap` entries — both were already generic, not scoped to `gitCommitAll`/`gitDiscardAll`, so no new error taxonomy was needed. Both RPC calls use `AbstractApiClient.callUnary`'s `'caller-signal-only'` timeout policy, the same as `gitCommitAll`/`gitDiscardAll`, since a pull or push is a network operation that should run to completion (or the caller's own cancellation) rather than time out under a budget picked for local reads; the Files tree threads the click's own `AbortSignal` through both calls so a stuck credential prompt or unreachable remote can be cancelled from the UI instead of hanging forever.

**A rebase conflict leaves the repository mid-rebase; `discardAllChanges` recognizes that state and runs `git rebase --abort` instead of its ordinary reset.** During a rebase, `HEAD` transiently points at the commit currently being replayed, not the branch's own pre-rebase tip — the ordinary `reset` + `checkout -- .` pair would "discard" onto that transient commit and leave the branch detached with the conflicted files still on disk. `discardAllChanges` now checks `isRebaseInProgress` (a `rebase-merge`/`rebase-apply` state directory present under `.git`, located via `rev-parse --git-path` and resolved against the repository root since `--git-path` prints a path relative to `-C`'s target, not this process's own cwd) before choosing its recovery: mid-rebase, it runs `git rebase --abort`, which restores the branch's pre-rebase tip and working tree in one step; otherwise it takes the original path. This makes the Files tree's existing Discard-all control double as the pull-conflict recovery action — no new UI surface — and its confirmation dialog's description names this case. `classify()` also gained a dedicated `X` status code for an unmerged (conflicted) porcelain pair (`DD`/`AU`/`UD`/`UA`/`DU`/`AA`/`UU`), checked before `??`, so a conflict reads as "Conflict" rather than collapsing into the same `U` ("Untracked") label a plain new file gets — the two are otherwise indistinguishable in the tree, and Discard's contract ("an untracked file is left untouched") would read as a safety promise for a conflicted file it does not actually protect.

**Client and UI threading mirrors `commitAllWorkspaceChanges`/`discardAllWorkspaceChanges`.** `IWorkspaces` gains `pullRebaseWorkspace`/`pushWorkspace`; `WorkspaceRuntime` implements each as a thin `this.api.workspace.{gitPullRebase,gitPush}(...)` call; `WorkspaceBrowserInjected`/`WorkspaceBrowser`/`SessionTree`/`FilesNodeProps` each gain the matching props (`pullRebase`/`push` on `FilesNodeProps`, matching the shorter `commitAllChanges`/`discardAllChanges` naming already used there).

**Pull and Push are unconditional icon buttons, unlike Commit/Discard which only appear once there are pending changes.** Whether there is anything to pull or push does not depend on the local `files` change map `GitStatusSummary` already has in hand — only a live network round-trip could answer that, which this feature deliberately does not add (see alternatives) — so both buttons render whenever the header shows a branch at all, positioned after Discard and before the existing Refresh control. Each has its own `pending`/`error` state (`pullPending`/`pullError`, `pushPending`/`pushError`); a single derived `busy` flag (`discardPending || discardConfirming || pullPending || pushPending`) disables every other write trigger (Commit, Discard, and whichever of Pull/Push isn't itself in flight) while one is running, since all four mutate the same git working tree/index and concurrent subprocesses would race on it. While its own action is pending, Pull/Push each also render an adjacent enabled Cancel button (aborting the in-flight `AbortSignal`) alongside their own disabled trigger — a plain disabled icon would give a hung network call no escape hatch. A pull failure refreshes git status and bumps `levelRefreshKey` the same as a success, since a rebase conflict changes working-tree content (unmerged files) just as much as a clean rebase does — this is what surfaces Discard-all as the visible recovery action. Starting any of the four actions (or clicking Refresh) clears every stale error notice, not only its own, so a fixed-in-a-terminal problem doesn't leave an old alert pinned under the header indefinitely.

**A successful Pull refreshes git status and bumps `levelRefreshKey`; a successful Push does neither.** A rebase can change working-tree file content the same way a commit or discard can, so Pull needs the same "remount the currently expanded level" treatment `commitAllChanges`/`discardAllChanges` already trigger. Push never touches the local working tree, and `WorkspaceGitStatus` carries no ahead/behind field for it to update, so there is nothing to refresh on push success.

**Two new hand-drawn icons**, matching the existing 14px stroke-based style (`strokeWidth 1.3`, round caps) `IconArrowUpOutline14`/`IconUndoOutline14` already established, added right after them in `ui-primitives`: `IconArrowDownOutline14` (Pull) — the vertical mirror of `IconArrowUpOutline14`'s path, base line at top instead of bottom — and `IconChevronDuoUpOutline14` (Push) — two stacked ascending chevrons. Push deliberately does not reuse `IconArrowUpOutline14`: that glyph is already the Commit icon in the same toolbar, and reusing it for Push would make two different actions look identical whenever both are showing (i.e. whenever there are also pending local changes). Cancel reuses the existing `IconCloseFill14` (already GitCommitInput's own Cancel glyph) rather than adding a third icon.

**`workspace-git.ts` shells out through the shared `dsh-native-command` runner** (`runNativeCommand`, already used elsewhere in this package for the native path opener) instead of a locally hand-rolled `promisify(execFile)`, picking up its Windows console hide and shared abort-propagation behavior for free; a thin `runGit` wrapper backs an absent caller signal with a controller nothing triggers, since every function in this module keeps `signal` optional while `runNativeCommand` itself requires one.

**Tests exercise real git remotes and real conflicts, not stubs.** `workspace-git.spec.ts` gained `initBareRemote`/`cloneRepo` helpers that `git init --bare` a second temp directory and clone it into the working copy under test, so `pullRebase` has a real upstream to fetch from and `push` has a real remote to land commits in — a rebase conflict is exercised by diverging the same file on both sides, a non-fast-forward push by diverging the remote from under the pusher before it ever pushes, and the explicit-refspec fix by setting `push.default: matching` with a second diverged branch that must NOT be pushed alongside the current one.

## Alternatives considered

- **Gating Pull/Push visibility on an ahead/behind count**, the way Commit/Discard gate on `changedCount > 0`. Rejected: computing that would need either a live `git fetch --dry-run`/`rev-list` round-trip on every Files-tree render (the same "no live push channel, no standing filesystem watcher" cost `gitStatus`'s own Alternatives section already rejected for its refresh mechanism) or trusting a stale local guess; showing both buttons unconditionally, like Refresh, needed neither.
- **Reusing `IconArrowUpOutline14` for Push**, since "push" and "commit" are both semantically "send upward." Rejected: the same icon appearing twice with different meanings in one toolbar (once for Commit, once for Push) whenever both are visible together would be actively confusing, not merely redundant.
- **A confirmation dialog for Push**, mirroring Discard's destructive-action `Modal`. Rejected: a push is reversible from the remote side (another push, or a revert) and git itself already refuses a non-fast-forward push by default — there is no "restore lost work" story a confirmation would meaningfully protect against, unlike Discard's irreversible local overwrite.
- **A dedicated "Abort rebase" button** as the pull-conflict recovery action, instead of folding it into Discard-all. Rejected: it would duplicate a destructive-action affordance the toolbar already has, and "discard everything, get back to clean" is exactly what aborting an in-progress rebase means — a separate button would force the user to know which of two similarly-destructive controls applies to their current state.
- **Swapping the Pull/Push trigger itself for a Cancel button while pending**, rather than rendering Cancel alongside a disabled trigger. Rejected: it discards the pending-disabled-button affordance the toolbar already establishes for visual consistency across all four write actions, for no behavioral gain over an adjacent button.

## Consequences

- New functions `pullRebase`, `push`, `currentRemote`, `isRebaseInProgress` in `packages/host/apiproxy/src/workspace-git.ts`; `discardAllChanges` branches on `isRebaseInProgress`; `classify()` gained the `X` (unmerged/conflict) code. New RPC methods `workspace.gitPullRebase`/`workspace.gitPush`, request `{ workspaceId }`, response `{ pulled: true }`/`{ pushed: true }`, both throwing `git-not-a-repository`/`git-command-failed` (no new `RpcErrorDetailsMap` entries; their JSDoc now names all four git write methods, not only `gitCommitAll`/`gitDiscardAll`).
- `IWorkspaces`, `WorkspaceBrowserInjected`, and `FilesNodeProps` each gain `pullRebaseWorkspace`/`pushWorkspace` (`pullRebase`/`push` on `FilesNodeProps`); `TestWorkspaces` and `FixtureApiClient` both implement the two new methods (the fixture, having no real git working tree, resolves them through the same `git-not-a-repository` error path `gitCommitAll`/`gitDiscardAll`/`gitFileDiff` already use); `TestWorkspaces`'s own verb-coverage test in `runtime.client.spec.tsx` now calls both.
- Two new hand-drawn icons in `ui-primitives`: `IconArrowDownOutline14`, `IconChevronDuoUpOutline14` (no Figma source); the icon-set regression test's hardcoded total moved from 73 to 75.
- New locale keys `files.git.pull`, `files.git.push`, `files.git.status.X` in both `zh` and `en`; `files.git.discardConfirmDesc` now names the mid-rebase-abort case.
- `workspace-git.ts` no longer imports `node:child_process`/`node:util` directly; it depends on `@deepseek-ai/dsh-native-command` (already a package dependency via the native path opener).
- Every touched file reaches 100% line/branch/function coverage in its own package suite; the narrow "signal aborts between the repo-root check settling and the git subprocess call settling" window `commitAllChanges`/`discardAllChanges` already document is `v8 ignore`d the same way for the new `rebase-abort` and `currentRemote` catch sites, not portably raceable in a test.
- `packages/host/apiproxy/README.md` and `README.zh.md` are paired in this same change (translation-pairing does not defer to a follow-up commit for this feature area).
