# Agent Note: Workspace Files tree gets git Pull (rebase) and Push

Status: implemented

## Problem

The Files tree's git toolbar ([git-status Agent Note](2026-08-27-workspace-files-git-status.md)) already shows branch/status and offers Commit-all/Discard-all, but a user with a configured remote had no way to sync with it from inside the app — pulling or pushing meant leaving for a terminal.

## Decision

**Two more RPC methods, `workspace.gitPullRebase({ workspaceId })` and `workspace.gitPush({ workspaceId })`, complete the same six-layer template `gitStatus`/`gitCommitAll`/`gitDiscardAll` already established.** Both delegate to new `workspace-git.ts` functions, `pullRebase` and `push`, which resolve the repository root the same way the write actions do (`repoRootOrThrow`, throwing `GitNotARepositoryError` rather than quietly no-opping — a sync the caller believes succeeded must not silently fail) and shell out to `git pull --rebase`/`git push` with no extra arguments: both act on the current branch and its already-configured upstream/remote, with no override surface. A failing command throws `GitCommandError('pull', …)`/`GitCommandError('push', …)`, reusing the existing `git-not-a-repository`/`git-command-failed` `RpcErrorDetailsMap` entries — both were already generic, not scoped to `gitCommitAll`/`gitDiscardAll`, so no new error taxonomy was needed. Both RPC calls use `AbstractApiClient.callUnary`'s `'caller-signal-only'` timeout policy, the same as `gitCommitAll`/`gitDiscardAll`, since a pull or push is a network operation that should run to completion (or the caller's own cancellation) rather than time out under a budget picked for local reads.

**Client and UI threading mirrors `commitAllWorkspaceChanges`/`discardAllWorkspaceChanges` exactly.** `IWorkspaces` gains `pullRebaseWorkspace`/`pushWorkspace`; `WorkspaceRuntime` implements each as a thin `this.api.workspace.{gitPullRebase,gitPush}(...)` call; `WorkspaceBrowserInjected`/`WorkspaceBrowser`/`SessionTree`/`FilesNodeProps` each gain the matching props (`pullRebase`/`push` on `FilesNodeProps`, matching the shorter `commitAllChanges`/`discardAllChanges` naming already used there).

**Pull and Push are unconditional icon buttons, unlike Commit/Discard which only appear once there are pending changes.** Whether there is anything to pull or push does not depend on the local `files` change map `GitStatusSummary` already has in hand — only a live network round-trip could answer that, which this feature deliberately does not add (see alternatives) — so both buttons render whenever the header shows a branch at all, positioned after Discard and before the existing Refresh control. Each has its own `pending`/`error` state (`pullPending`/`pullError`, `pushPending`/`pushError`), disabling its own button while in flight and rendering its error as a `role="alert"` notice, mirroring `discardPending`/`discardError`'s shape — but neither opens a confirmation dialog or takes free-text input, since neither action has anything to confirm or type; a direct click is the entire interaction, closer to Refresh's shape than Commit's.

**A successful Pull refreshes git status and bumps `levelRefreshKey`; a successful Push does neither.** A rebase can change working-tree file content the same way a commit or discard can, so Pull needs the same "remount the currently expanded level" treatment `commitAllChanges`/`discardAllChanges` already trigger. Push never touches the local working tree, and `WorkspaceGitStatus` carries no ahead/behind field for it to update, so there is nothing to refresh on push success.

**Two new hand-drawn icons**, matching the existing 14px stroke-based style (`strokeWidth 1.3`, round caps) `IconArrowUpOutline14`/`IconUndoOutline14` already established, added right after them in `ui-primitives`: `IconArrowDownOutline14` (Pull) — the vertical mirror of `IconArrowUpOutline14`'s path, base line at top instead of bottom — and `IconChevronDuoUpOutline14` (Push) — two stacked ascending chevrons. Push deliberately does not reuse `IconArrowUpOutline14`: that glyph is already the Commit icon in the same toolbar, and reusing it for Push would make two different actions look identical whenever both are showing (i.e. whenever there are also pending local changes).

**Tests exercise real git remotes, not stubs.** `workspace-git.spec.ts` and `api-proxy-workspace-files.spec.ts` both gained `initBareRemote`/`cloneRepo`(`cloneInto`) helpers that `git init --bare` a second temp directory and clone it into the working copy under test, so `pullRebase` has a real upstream to fetch from and `push` has a real remote to land commits in — a rebase conflict is exercised by diverging the same file on both sides, a non-fast-forward push by diverging the remote from under the pusher before it ever pushes.

## Alternatives considered

- **Gating Pull/Push visibility on an ahead/behind count**, the way Commit/Discard gate on `changedCount > 0`. Rejected: computing that would need either a live `git fetch --dry-run`/`rev-list` round-trip on every Files-tree render (the same "no live push channel, no standing filesystem watcher" cost `gitStatus`'s own Alternatives section already rejected for its refresh mechanism) or trusting a stale local guess; showing both buttons unconditionally, like Refresh, needed neither.
- **Reusing `IconArrowUpOutline14` for Push**, since "push" and "commit" are both semantically "send upward." Rejected: the same icon appearing twice with different meanings in one toolbar (once for Commit, once for Push) whenever both are visible together would be actively confusing, not merely redundant.
- **A confirmation dialog for Push**, mirroring Discard's destructive-action `Modal`. Rejected: a push is reversible from the remote side (another push, or a revert) and git itself already refuses a non-fast-forward push by default — there is no "restore lost work" story a confirmation would meaningfully protect against, unlike Discard's irreversible local overwrite.

## Consequences

- New functions `pullRebase`, `push` in `packages/host/apiproxy/src/workspace-git.ts`; new RPC methods `workspace.gitPullRebase`/`workspace.gitPush`, request `{ workspaceId }`, response `{ pulled: true }`/`{ pushed: true }`, both throwing `git-not-a-repository`/`git-command-failed` (no new `RpcErrorDetailsMap` entries).
- `IWorkspaces`, `WorkspaceBrowserInjected`, and `FilesNodeProps` each gain `pullRebaseWorkspace`/`pushWorkspace` (`pullRebase`/`push` on `FilesNodeProps`); `TestWorkspaces` and `FixtureApiClient` both implement the two new methods (the fixture, having no real git working tree, resolves them through the same `git-not-a-repository` error path `gitCommitAll`/`gitDiscardAll`/`gitFileDiff` already use).
- Two new hand-drawn icons in `ui-primitives`: `IconArrowDownOutline14`, `IconChevronDuoUpOutline14` (no Figma source); the icon-set regression test's hardcoded total moved from 73 to 75.
- New locale keys `files.git.pull`, `files.git.push` in both `zh` and `en` — button titles only, no placeholder/confirm keys, since neither action opens a modal or takes input.
- Every touched file reaches 100% line/branch/function coverage in its own package suite; `workspace-git.ts`'s two new abort-guard branches (the same narrow "signal aborts between the repo-root check settling and the git subprocess call settling" window `commitAllChanges`/`discardAllChanges` already document) are `v8 ignore`d per the same precedent, not portably raceable in a test.
- The English `packages/host/apiproxy/README.md` update is not yet paired with its `zh` counterpart; a follow-up bilingual pass through `dsh-translate-docs` is required before `verify-translation-pairing` passes again, matching this feature area's own precedent (the git-status feature's translation commit landed separately from its implementation commit).
