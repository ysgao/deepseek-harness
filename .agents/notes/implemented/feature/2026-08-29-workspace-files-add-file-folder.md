# Agent Note: Workspace Files tree gains Add-file/Add-folder actions

Status: implemented

English | [中文](2026-08-29-workspace-files-add-file-folder.zh.md)

## Problem

The Workspace Files tree ([sibling-browser](2026-08-24-workspace-files-sibling-browser.md), [git status](2026-08-27-workspace-files-git-status.md) Agent Notes) browses, previews, edits, and diffs existing files, but has no way to create a new one: a user who wants to add a file or folder must leave the app and use the OS file manager or a terminal, then use the tree's own Refresh action to see it. `workspace.listEntries`/`workspace.readFile`/`workspace.writeFile` already establish the "Files-tree-only host primitive, unsandboxed, direct `node:fs/promises` calls" pattern (`files.ts`); file/folder creation needed the same shape of addition, distinct from `writeFile` (which only ever overwrites an existing file).

## Decision

**Two new `@Remote` methods, `workspace.createFile`/`workspace.createDirectory`, built on the `listEntries`/`readFile`/`writeFile` template.** Both take a `WorkspaceCreateEntryRequest { workspaceId, parentPath, name }` — a parent directory plus a single name segment, not a caller-joined path, so the wire request cannot smuggle a path separator into `name` to escape `parentPath`. `file-commands.ts`'s new `requireContainedChildPath` validates `name` (non-blank, not `.`/`..`, no `/`/`\`) before resolving `parentPath` through the existing `requireContainedPath` workspace-root containment check, then joins the two — the same order `directory-picker.ts`'s existing `createDirectory(path, name)` validates its own name segment, reused here as precedent rather than shared code (the two seams stay independent: this one is workspace-root-contained and Files-tree-specific, that one is the picker's own directory-only browse).

**`files.ts` gains `createWorkspaceFile`/`createWorkspaceDirectory`, both host primitives that fail loud on an existing target rather than silently succeeding or overwriting.** `createWorkspaceFile` calls `node:fs/promises.writeFile` with `flag: 'wx'` (create-exclusive — rejects with `EEXIST` on an existing path, so it can never truncate real content, unlike `writeFile`'s deliberate version-guarded overwrite). `createWorkspaceDirectory` calls `mkdir` with `recursive: false` — exactly one new path segment, never silently creating a chain of missing parents. `WorkspaceFileError` gains two codes shared by both primitives: `already-exists` (the node:fs `EEXIST` case) and `parent-missing` (`ENOENT` — the enclosing directory does not exist); `types.ts`'s `WorkspaceErrorDetailsMap` gains matching entries plus `invalid-name` for the request-level segment check.

**Client and UI threading mirrors `writeFile`'s sibling props exactly.** `IWorkspaces` gains `createFile`/`createDirectory` (workspaceId, parentPath, name, signal → the created path); `ClientWorkspaceModel`/`WorkspaceController` (the Client service face) each implement a thin pass-through, using the existing `WorkspaceFileBrowseError` wrapper (not a new error class) since these failures are discriminated by `error.name` the same way a `readFile`/`writeFile` rejection already is. `WorkspaceBrowserInjected`/`WorkspaceBrowser`/`SessionTree`/`FilesNodeProps` each gain `createWorkspaceFile`/`createWorkspaceFolder` alongside the existing file props.

**Two new icons, `IconNewFile16`/`IconNewFolder16`**, join the existing four `(hand-drawn, stroke-based, no figma source)` glyphs (`ic_ds_arrow_up_outline_14` and its three siblings) as a fifth and sixth: each is the existing file-placeholder/folder-close outline, shrunk and shifted up-left, with a small filled-circle-plus badge (12%-opacity `currentColor` circle + a plus stroke) riding the bottom-right corner — the exact "default icon modified with a small plus in the corner" composition requested, drawn as one flat SVG rather than a runtime overlay (consistent with every other icon in this set being a self-contained component).

**The Add-file/Add-folder buttons sit in the Files header, always visible — unlike the git action group (`GitStatusSummary`), which renders nothing outside a git working tree.** A new `AddEntryButtons` component renders unconditionally before the git branch/status display; clicking either opens `CreateEntryInput`, an inline name field that replaces the header's trailing group in place (the same swap `GitCommitInput` already does for the Commit action) — Enter submits, Escape cancels, a Check/Close icon pair offers the same two actions by click.

**A directory row's own click both expands/collapses it and marks it the create-target**, rather than adding a separate selection gesture: `FilesNode` tracks `selectedDirPath: string | null` (null = workspace root), threaded down through `FilesLevel`/`DirectoryRow` alongside the existing `gitStatusFiles` prop; the most recently clicked directory gets a persistent `.rowSelected` highlight (distinct from `:hover`, using the theme's `--dsw-alias-interactive-bg-active` token) that survives after the pointer moves away, and stays the create-target even if the row is later collapsed again. Collapsing or reopening the Files node itself (the root header row's own toggle) always resets the target back to the workspace root — a stale selected subdirectory from a prior expansion must not silently outlive the tree instance that showed it. Submitting Add-file/Add-folder calls `createWorkspaceFile`/`createWorkspaceFolder` with `selectedDirPath ?? rootPath`, then on success bumps the existing `levelRefreshKey` (the same "a write action changed the tree, remount the currently expanded level" mechanism `commitAllChanges`/`discardAllChanges`/`pullRebase` already use) so the new entry appears once its parent directory is (or becomes) expanded.

**Only one write action may run at a time**, extending the existing `busy` gate (`discardPending || discardConfirming || pullPending || pushPending`) with `createPending` — creating a file/folder also touches the working tree the git actions mutate, so they share the same single-writer discipline. A create failure (`already-exists`, `parent-missing`, `invalid-name`, or a generic I/O error) shows an inline notice and leaves the input open rather than closing it, so retrying the same name after fixing the underlying cause (or after the caller renames the conflicting file elsewhere) needs no re-opening of the Add flow.

## Alternatives considered

- **A single `createEntry({ workspaceId, parentPath, name, kind })` RPC method instead of two.** Rejected: `listEntries`/`readFile`/`writeFile` are already one-verb-per-operation on this Controller, and a file vs. directory creation has different host primitives (`writeFile` with `wx` vs. `mkdir`) and different response shapes (`WorkspaceCreateFileValue` carries a content version, `WorkspaceCreateDirectoryValue` does not) — a shared verb would need a discriminated request/response pair for no reduction in surface area.
- **Recursive directory creation (`mkdir` with `recursive: true`), silently creating missing intermediate parents.** Rejected: the product request is "create a new file/folder" at an explicit, already-visible location (the workspace root or a directory the user just clicked), not "create an arbitrary nested path" — silently manufacturing intermediate directories the user never asked for and cannot see until the tree refreshes would be a surprising side effect. `parent-missing` surfaces the same condition as a rejection instead.
- **A separate `<button>`/context-menu affordance for "select this folder as target", independent of the row's own expand/collapse click.** Rejected per direct product feedback: the two gestures share one click, so a folder need not stay expanded to remain the create-target, and no second interaction surface has to be designed, styled, or tested.
- **The Add-file/Add-folder controls placed in the tab bar (Chat/File/Trajectory), visible only while the File tab is active.** Rejected in favor of the Files tree's own header — the create action's natural home is beside the existing git actions on the same row, not a second location a user must learn.
- **Overwriting an existing target instead of failing with `already-exists`.** Rejected: `writeFile` already owns the "guarded overwrite" behavior via `expectedVersion`; a bare "create" action silently clobbering existing content on a name collision would be a data-loss surprise with no confirmation step.

## Consequences

A user can create a new empty file or folder directly under the workspace root, or under any directory they have clicked (expanded or not), without leaving the app; the new entry appears in the tree once its parent is expanded, the same way a commit or discard already surfaces a changed working tree. The Add-file/Add-folder buttons work in a workspace with no git repository at all, unlike every other action in the header. Creating a file does not open it — the user still clicks the new row to preview or edit it, matching how a freshly committed or pulled file is discovered today. `already-exists`/`parent-missing`/`invalid-name` are additions to the shared `WorkspaceErrorDetailsMap` closed-code vocabulary and therefore visible to every existing consumer that exhaustively switches on it; none did before this change (checked: `FileView.tsx`, `FileViewer.tsx`, `FilesNode.tsx` all narrow only the codes they specifically handle and fall through generically otherwise).
