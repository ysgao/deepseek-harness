# Agent Note: Workspace Files Refresh fetches from the remote; Pull only rebases

Status: implemented

English | [中文](2026-08-30-workspace-files-git-fetch.zh.md)

This note builds on the [Pull/Push ahead/behind gating decision](2026-08-30-workspace-files-git-pull-push-gating.md): that note made Pull/Push visibility depend on `ahead`/`behind`, but left those counts as accurate only as of whatever a prior fetch/pull/push happened to leave in the local remote-tracking refs — with no in-app action that ever fetched on its own. This note adds that action.

## Problem

A repository could be genuinely behind its remote with no way for a user to discover it from inside the app: `ahead`/`behind` are computed from already-known local refs (`git rev-list --left-right --count @{upstream}...HEAD`), and nothing calls `git fetch` anywhere in the existing flow — not on mount, not on the explicit Refresh click, not on collapse-then-reopen. The Pull button, gated on `behind > 0`, would then never appear even with real upstream commits waiting, until something external (a terminal `git fetch`, or a previous in-app Pull/Push) happened to update the local tracking ref first. Manually running `git fetch` in the same repository this Files tree points at was enough to make a previously invisible Pull button with an accurate count appear immediately, confirming the counts themselves were correct — only the missing fetch trigger was the gap.

## Decision

**A new `workspace.gitFetch({ workspaceId })` RPC method, completing the same `@Remote`-method template `gitStatus`/`gitCommitAll`/`gitDiscardAll`/`gitPullRebase`/`gitPush` already use on `WorkspaceController`.** It delegates to a new `fetchRemote` function in `workspace-git.ts`, which runs a bare `git fetch` (no arguments — the default remote's every tracked branch) and resolves `{ fetched: true }` on success. `git fetch` never touches `HEAD`, the current branch, or the working tree — it only updates remote-tracking refs (`refs/remotes/origin/*`) — so it cannot conflict and never changes anything `workspaceGitStatus`'s `files` map reports; only `ahead`/`behind` (computed from those same refs) can change as a result. Failure modes are asymmetric and both real: an unreachable or misconfigured remote throws `GitCommandError`, but a repository with literally no remote configured at all resolves successfully as a documented git no-op (verified empirically) rather than failing — `fetchRemote` does not special-case this; it simply reports whatever `git fetch` itself reports.

**The Files tree header's Refresh control calls `fetchRemote` before its existing local git-status re-read; no other trigger does.** `FilesNode`'s `handleRefresh` now awaits `fetchRemote(workspaceId)` first, then calls the same `refreshGitStatus()` it always called — on fetch failure, it still calls `refreshGitStatus()` afterward (whatever is already locally known may be worth re-displaying, e.g. a commit made from a terminal since the last read) while also surfacing a new `fetchError` notice, styled identically to the existing `pullError`/`pushError`/`commitError`/`discardError` banners. Every other route to a status re-read — the initial mount, collapse-then-reopen, and the post-commit/discard/pull/push refreshes — stays exactly as before, calling `refreshGitStatus()` directly with no fetch: those are automatic/implicit re-reads triggered by an unrelated user gesture (opening the tree, committing, pushing), and a surprise network call (with its possible credential prompt) at one of those moments would be more surprising than helpful. Refresh's own fetch is deliberately exempt from the header's shared `busy` flag in both directions: since a fetch touches neither the working tree nor the index, it may run alongside Commit/Discard/Pull/Push instead of waiting for them, and the reverse also holds — Commit/Discard/Pull/Push stay enabled while a fetch is in flight. Refresh guards only against its own re-entrancy, via a new `fetchPending` state that disables the Refresh button itself (not the other triggers) until its own fetch settles.

**`pullRebase` no longer fetches: it now runs bare `git rebase` (no arguments) instead of `git pull --rebase`.** `git rebase` with no `<upstream>` argument resolves the same default upstream `git pull` itself would (`branch.<name>.remote`/`branch.<name>.merge`), so this preserves exactly what branch Pull rebases onto — it simply removes the implicit fetch `git pull --rebase` used to perform first. This decouples "check for updates" (now Refresh's job) from "apply already-known updates" (Pull's job): before this change, a Pull click could silently fetch commits beyond whatever `behind` count the header displayed, rebasing more than what the user saw and clicked for. After this change, Pull always rebases onto exactly the commits Refresh's last fetch already found — the displayed count and the rebase's actual effect can never diverge. A Pull clicked with a genuinely stale local upstream ref (no Refresh ever run, or run long ago) simply rebases onto that stale ref, the same "as fresh as the last fetch" contract `ahead`/`behind` themselves already carry.

## Alternatives considered

- **Having `gitStatus` (or `aheadBehind`) fetch on every call**, so mount, collapse-then-reopen, and Refresh would all report accurate counts without a separate action. Rejected: `gitStatus` is read on the Files tree's every expand and on every write action's post-success refresh — turning all of those into network round trips (with possible credential prompts) reintroduces exactly the cost the git-status note's own "no live push channel" alternative rejected for a different reason (a standing watcher); an explicit, single Refresh click is the narrowest place to accept that cost.
- **Keeping `pullRebase` as `git pull --rebase`** (fetch-and-rebase in one command), now that a separate `gitFetch` exists, treating the two as independent-but-overlapping capabilities. Rejected: with both Refresh and Pull each doing their own fetch, the count Refresh just displayed and the commits Pull's own later fetch would apply could silently diverge if the remote changed in between two clicks — decomposing the two into fetch (Refresh) and rebase-only (Pull) is what removes that possible divergence.
- **A dedicated Cancel affordance for Refresh's own fetch**, mirroring Pull/Push's adjacent Cancel button while pending. Rejected for now: unlike `pullRebase`/`push`, Refresh has never had pending/cancel semantics before this change, and a plain fetch has no working-tree-mutation consequence to escape from if left running — `fetchPending` disabling the button against re-entrant double-clicks is enough.
- **Folding a fetch failure into total silence** (no error notice), on the theory that "nothing to report" already covers "couldn't check." Rejected: the user explicitly clicked Refresh to check for real; silently doing nothing on failure would look identical to "you're already in sync" and could hide a real, actionable problem (expired credentials, network down).

## Consequences

- `WorkspaceGitFetchValue` (`{ fetched: true }`) added to `packages/api/workspace-controller/src/types.ts`; new `fetchRemote` function in `workspace-git.ts`; new `gitFetch` methods on `WorkspaceFileCommands`/`WorkspaceController`/`ClientWorkspaceModel`, new `fetchRemote` on `IWorkspaces`/`WorkspaceController` (client), new `fetchWorkspaceRemote` on `WorkspaceBrowserInjected` and its `apply.ts` wiring, new `fetchRemote` on `FilesNodeProps`, threaded through `SessionTree`/`WorkspaceBrowser` the same way `pullRebase`/`push` already are.
- `pullRebase` in `workspace-git.ts` now shells out to `git rebase` instead of `git pull --rebase`; its `GitCommandError` command label changed from `'pull'` to `'rebase'` (and `GitCommandError`'s own JSDoc list of possible labels gained `fetch`/`rebase`).
- `FilesNode.tsx` gained `fetchPending`/`fetchError` state and a new error notice; `handleRefresh` is now async (fetch, then refresh, with error handling on the fetch leg only); the Refresh button gained `disabled={fetchPending}`.
- Locale key `files.git.refresh` (both `zh` and `en`) now documents that it fetches without rebasing.
- Every existing test double implementing `IWorkspaces`/`WorkspaceRemote` (`test-support/client-runtime`, the package's own `transport`/`model` specs, `workspaces-service.client.spec.ts`) gained the new method; the `TestWorkspaces` verb-coverage test in `runtime.client.spec.tsx` now calls it too.
- `workspace-git.host.spec.ts`'s existing `pullRebase` tests now call `fetchRemote` first where they need real upstream commits present to rebase onto or conflict with (a bare `pullRebase` with no prior fetch has nothing new to apply, verified directly by a dedicated assertion); a new `fetchRemote` describe block covers a real remote-tracking-ref update, an unreachable-remote failure, a no-remote-configured no-op success, and abort propagation.
- Every touched file reaches 100% line/branch/function coverage in its own package suite.
